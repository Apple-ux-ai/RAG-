# RAG 结构化商品上下文设计

日期：2026-10-24
状态：已批准，已实施，待代码审查
范围：印尼兄弟店铺的 IM→RAG 回复链路

## 目标

客户询问当前浏览的产品时，回复使用产品卡片和聊天记录中已知的信息，不重复询问目的地、产品时长或出发城市。价格和包含项目以现有 FAQ/知识库为准；日期、人数等未提供的信息不作猜测，只在回答确实需要时询问。

## 当前情况

- 产品咨询卡片可提供产品 ID、产品名称、出发城市、标签等字段；截图中的卡片没有出发日期或同行人数。
- IM 当前把产品卡片转成普通历史文本发送给 RAG。
- `/v1/chat` 没有结构化商品字段，调用 `handle_customer_message` 时产品 ID 和名称为空，客服侧无法可靠解析当前产品。
- 该卡片表示客户从产品详情页发起咨询，不代表已下单或已确认预订。

## 方案选择

1. **结构化传递商品上下文（本设计选择）**：IM 从最近的产品卡片中提取白名单字段，通过可选 `product_context` 传给 RAG。服务端把产品 ID、名称、出发城市和标签作为标注清楚的上下文；从产品名称识别目的地与行程时长。字段缺失时保持未知。契约清楚且便于单测，需同步改 IM 适配器与 RAG 接口。
2. 从聊天历史里的卡片文本做正则解析：不新增请求字段，但依赖文本格式和历史窗口；卡片被截断或格式改变时可能再次丢失上下文。
3. 只调整提示词：改动最少，但模型只能从普通历史文本猜商品信息，无法可靠解决本次重复提问。

## 实施设计

- 在 IM 适配器中，当前产品卡片优先；否则选本会话最近一张卡片，并把该卡片作为完整记录使用，不跨卡片补字段。各字段遵守 API 长度限制，超长字段直接省略。生成可选 `product_context`。只发送 `product_id`、`product_name`、`departure_city`、`product_label`；不发送产品链接、来源备注或会员标签。
- 在 RAG API 中为 `product_context` 增加严格校验且保持字段可选，以兼容其他现有调用方。将产品 ID 和名称传入现有客服处理入口，并把出发城市和标签作为明确标注的上下文传入提示词。商品标题作为不可信数据放在 user 消息中，解析指令保持静态且与标题分开；优先从目的地目录提取标题中完整的已知目的地和行程时长，避免接受不完整子串或把营销后缀当目的地，无法识别时才考虑模型结果。商品字段视为元数据，不执行字段值中可能出现的指令。
- 提示词将卡片称为“当前浏览的产品/线路”，不能称作已购买订单；不得把出发城市混作目的地。产品名称中的目的地和天数、独立的出发城市、客户对话中明确提供的要求都是已知项，不重复询问。
- 缺少的日期、人数仍然未知。价格问题先根据 FAQ 回答已知包含项与不包含项；资料不足时简短说明需要核实，并只询问核价所需的缺失信息。
- 不改 IM 监听、发送、确认流程，不接入付款订单或客户资料数据库，不扩大到其他店铺。

## 验收

- IM 测试覆盖从产品卡片构造 `product_context`，且只包含白名单字段。
- RAG API 测试覆盖结构化字段映射到客服处理入口，以及不带该字段的旧请求仍兼容。
- 以合成上下文验证：产品目的地、天数、出发城市不会被重复询问；未提供的日期、人数不被伪造；不确定的价格/包含项不会被编造。
- 不发送真实 IM 消息作为自动化测试。
